# 需求规格

> 状态：待评审｜规格版本：0.1｜更新日期：2026-09-23

| ID | 需求 | 验收摘要 |
| --- | --- | --- |
| ONT-01 | 系统应按知识库保存节点、关系、属性、别名、来源和发布状态。 | 重启后可读取；不同知识库隔离。 |
| ONT-02 | 查询应识别标准名称及别名，并返回匹配实体、相邻关系、扩展词和结构化条件。 | “退钱没收到”可归一到“退款未到账”。 |
| ONT-03 | 原始问题的向量召回必须始终保留，不因图谱缺失或误识别而被阻断。 | 无图谱或无匹配时退化为普通向量检索。 |
| ONT-04 | 图谱结果应增强而非替代向量检索，可扩展查询、提供目标文档提示和排序信号。 | 结果中可观察检索策略与查询计划。 |
| ONT-05 | 权限、有效期、版本和适用范围属于确定性过滤职责，不得交给大模型自由决定。 | 后续过滤层必须位于模型上下文组装之前。 |
| ONT-06 | 图谱结论应能追溯到原始文档、切片、项目、流程或经验。 | 节点/关系支持 source 与 documentId 等证据引用。 |
| ONT-07 | 第一阶段应支持本体替换、读取、查询和混合检索 API。 | 契约校验失败返回 400；成功结果结构稳定。 |
| ONT-08 | 每个知识库应具备草稿、发布版本、候选事实、人工审核和正式提交闭环。 | 未审核候选不进入正式图谱；接受后提交可被查询规划命中。 |
| ONT-09 | 候选节点和关系必须至少携带一条文档证据。 | 契约拒绝无 evidence 的候选；提交后保留 documentId/chunkId。 |
| ONT-10 | 用户可选择知识库文档并用已配置的应用模型自动识别实体、关系和证据。 | 模型输出只形成待审核候选，不直接修改正式图谱；每条候选可追溯到原始切片。 |
| ONT-11 | 默认界面应采用“选择文档—AI 分析—人工审核—批准入库”流程，JSON 编辑仅作为高级能力。 | 业务用户无需编写 JSON；可逐条或批量接受/拒绝候选。 |
| ONT-12 | 多切片文档的自动识别应分批生成结构化结果，并在单批输出不完整时自动缩小范围重试。 | 大文档不再因一次模型输出过长而整体失败；源切片内容和证据边界保持不变。 |
| ONT-13 | 单条模型候选的证据无法在授权切片中核验时，应丢弃该候选而不是中止整篇文档分析。 | 可信候选继续进入审核区；引用无效节点的关系一并丢弃；未授权 chunkId 仍拒绝整次请求。 |
| ONT-14 | 知识库详情应提供可视化本体检索验证，展示查询规划、增强策略和最终知识片段。 | 用户无需调用 API 即可判断实体、别名、一跳关系和本体增强召回是否生效；验证操作只读。 |
| ONT-15 | 知识库详情应将已审核写入的正式本体以关系图展示。 | 用户可查看实体、关系、类型图例和属性详情，可搜索定位、切换布局及缩放；大图限制首屏节点数且不影响完整存储。 |

## 非目标

- 不建设完整企业级图数据库；
- 不实现三跳以上复杂推理；
- 不允许模型抽取结果未经审核自动成为正式制度；
- 不在第一阶段替换 LanceDB、云知识库或现有经验存储；
- 不允许模型抽取结果绕过人工审核直接写入正式图谱。
