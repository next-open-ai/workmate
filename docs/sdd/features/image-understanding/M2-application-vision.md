# VIS-M2 · 有目标的图片理解应用模型

状态：已实现，自动化工程闭环通过，待真实Provider/安装态验收。继承 M1 图片上传、会话鉴权、原图保留及最近4张边界。

## 需求与契约

- VIS-R6：新增 `vision` 应用模型能力，用户名称“图片理解”，复用 Provider 连接、能力默认模型绑定和员工 disabled/auto/preferred 授权。缺省关闭，不改主模型。
- VIS-R7：Pi 视觉主模型直接接收原图；文本主模型存在已授权 vision 绑定时，通过 `model_understand_images` 工具识图。无授权/绑定拒绝；不回退到图片生成或 Bash。M2 不扩大到多员工或其他引擎。
- VIS-R8：工具参数仅接受当前 Run 图片白名单内 `imageIds?` 和 `focus?`。原始用户问题由服务端当前消息绑定，不接受工具覆写；同时发送最近必要文字上下文（有长度上限）。Provider 只由 agent-core 调用。
- VIS-R9：返回 modelId、imageIds、originalQuestion、识图分析、usage 和“事实/推断/不确定性”的解释边界。不返回原图Base64，不声称描述等同原图。追问重新读取原图并携带新问题。
- VIS-R10：每个Run相同图片/问题/关注点复用结果（含失败，不自动反复重试）；最多3个不同识图请求。90秒超时及取消贯穿模型调用。沿用工具/能力进度事件显示“正在根据问题识别图片”。跨Run不缓存，避免跨用户和过期图片误用。
- VIS-R11：运行等待时间以服务端Run的`startedAt`为事实源；离开并返回对话、消息ID对齐或服务端重新水合不得从0重新计时。完成后使用`finishedAt-startedAt`固化耗时。
- VIS-R12：普通桌面对话不得为移动端镜像无条件轮询。进入对话时允许一次状态同步；只有用户实际创建手机对话入口后才启用周期同步。图片预览只在`sessionId`或`imageId`实际变化时重新加载，避免状态刷新触发重复下载原图、重复写KV和污染日志。
- VIS-R13：图片理解只携带最近两条必要上下文且上限2500字符，输出预算上限2048 tokens；避免无关长历史造成首包延迟和“与之前需求无关”等偏题判断。原始用户问题和原图不得裁剪。
- VIS-R14：同一Run内出现超时或Provider终止错误后，对图片理解能力立即熔断；返回`retryable=false`、模型和端点主机等可诊断信息，主模型不得通过改变`focus`连续重试。用户显式发起新一轮后方可重试。阿里专属MaaS兼容端点若从远程目录选到带日期的Qwen VL快照名，运行时使用已验证的稳定别名，标准DashScope端点和其他厂商不做该改写。
- VIS-R15：活动状态以服务端持久化Run为事实源。Run结束但缺失能力终态事件时不得将“处理中”推断成成功；服务端失败状态必须覆盖界面中的暂存状态。

## 设计与实现顺序

1. VIS-05：contracts/模型配置/员工授权增加vision；增量兼容v3，既有配置和M1不变。
2. VIS-06：统一Tool Backend接收Run图片上下文，注册工具并执行目标性多模态请求；图片引用不可由工具任意跨会话查找。
3. VIS-07：Pi历史按路由保留原图或仅暴露附件编号/引用；文本主模型永不收到图片内容块；服务端门禁与界面提示一致。
4. VIS-08：单测、真实Pi→本地mock主模型→工具→mock视觉模型→主模型回答集成回归；同步指南/任务/状态。
5. VIS-09：修复长耗时识图的计时恢复与桌面无条件轮询；保持SSE为运行进度主通道，稀疏Run轮询仅作断流兜底。
6. VIS-10：修复Provider超时后的盲目重试、模型/端点诊断和失败活动误显示为完成；SSE健康时将Run兜底查询降为低频。

VIS-M2-T3：模型类型、默认绑定、员工开关、上传可用状态/服务告知/不支持引擎、配置保存；类型检查及构建。

VIS-M2-T5：Provider失败后即使主模型改变关注点也不产生第二个上游请求；失败结果包含`retryable=false`和模型诊断；持久化失败活动覆盖本地暂存状态，未收到终态的能力活动不得被Run完成事件标成成功。

## 回滚与限制

关闭员工图片理解能力/移除vision绑定即可禁用新路径；原有视觉主模型路径不变。选择vision类型是用户对模型能力的显式声明；沿用Pi SDK中现有Provider协议，不新增厂商猜测规则。真实Provider质量、安装包、其他引擎端到端验收不以mock代替。
