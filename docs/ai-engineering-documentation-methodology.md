# AI 编程项目的工程文档体系与实践方法论

> 文档性质：可复用的工程方法与改造指南  
> 适用对象：AI 应用、Agent 平台、模型服务平台、AI 编程项目，以及需要人和编码智能体长期协作的软件项目  
> 版本：1.0  
> 更新日期：2026-09-23

## 1. 总体方案

AI 编程项目的文档不应只是代码完成后的说明材料，而应成为连接产品目标、架构决策、功能规格、实施任务、测试证据和发布运行的工程控制面。

这套方案采用“分层事实源 + SDD 功能包 + 生命周期成果 + 自动化文档站”的总体结构：

```text
产品目标与项目需求
        ↓
全局架构与 ADR
        ↓
功能 SDD：需求 → 设计 → 契约 → 计划 → 任务 → 测试 → 状态
        ↓
代码实现与自动化验证
        ↓
阶段成果、版本验收与部署运行
        ↓
反馈进入需求、架构决策和下一轮计划
```

核心思想是：每类事实只保留一个权威位置，通过稳定 ID 和链接建立追踪关系，而不是在多个 README、计划和测试报告中重复维护同一结论。

### 1.2 各层事实源

| 问题 | 权威位置 |
| --- | --- |
| 产品是什么、解决什么问题 | `docs/product/product-overview.md` |
| 项目有哪些能力和质量要求 | `docs/product/requirements-overview.md` |
| 当前系统边界和依赖方向是什么 | `docs/architecture/architecture.md` |
| 为什么选择某项长期架构方案 | Accepted ADR |
| 某个功能现在应该如何工作 | `docs/sdd/features/<feature>/` |
| 项目整体先做什么、后做什么 | `docs/planning/roadmap.md` |
| 某个功能具体如何实施 | 功能 SDD 的 `plan.md` 与 `tasks.md` |
| 当前做到哪里、有什么阻塞 | 功能 SDD 的 `status.md` |
| 应该如何测试 | 功能 `test-spec.md` 与项目 `quality/test-strategy.md` |
| 实际测试结果是什么 | `docs/quality/features/` 或 `quality/releases/` |
| 平台某项能力表现如何 | `docs/benchmarks/` |
| 某阶段评审时确认了什么 | `docs/deliverables/` |
| 如何部署、监控和回滚 | `docs/deploy/` |

## 2. 方案目的

### 2.1 为 AI 编程建立稳定上下文

编码智能体最常见的问题不是不会写代码，而是缺少稳定、完整、没有冲突的项目上下文。结构化文档让智能体可以按固定顺序读取规则、架构、功能规格、当前任务和测试要求，减少依靠猜测修改代码。

### 2.2 将自然语言意图变成可执行工程约束

需求必须具有稳定编号、明确范围、验收条件和非目标；设计必须说明模块边界、契约和状态变化；任务必须关联需求和测试。这样才能把“帮我实现某功能”转化为可验证的工程工作。

### 2.3 防止文档、代码和状态彼此失真

方案明确区分：

- 已写规格不等于已实现；
- 已实现不等于已测试；
- 测试通过不等于已发布；
- 当前规格不等于历史评审结论；
- Benchmark 得分不等于功能正确。

### 2.4 支持长期维护与多人、多智能体协作

通过单一事实源、稳定 ID、追踪矩阵和阶段成果，不同开发者、产品人员、测试人员和编码智能体可以在同一语义下协作，并在变更发生后快速判断影响范围。

## 3. 方案特点

### 3.1 规格与实现同仓

文档随代码评审、版本化和发布，避免外部文档系统与实际仓库长期分离。外部项目管理平台可以负责负责人、工期和实时协作，但不能替代仓库中的可执行规格。

### 3.2 全局架构与功能设计分离

全局架构只维护长期稳定的系统边界；功能细节进入独立 SDD 包。这样既避免全局架构无限膨胀，也避免每个功能重新解释整套系统。

### 3.3 当前规格与历史快照分离

- SDD 说明“现在应该是什么”；
- Deliverables 说明“当时评审通过了什么”；
- Archive 保存“已经被什么替代”；
- Releases 说明“某个版本实际发布了什么”。

### 3.4 测试与 Benchmark 分离

测试回答“是否正确、能否发布”，Benchmark 回答“表现如何、哪个方案更优”。Benchmark 默认不阻断发布；只有明确进入发布标准的指标才成为质量门禁。

### 3.5 对人和 AI 同时可读

目录、文件名、状态字段和 ID 既便于人工评审，也便于编码智能体按规则检索。VitePress 等工具在不改变 Markdown 事实源的情况下，提供搜索、导航、主题和离线 HTML 展示。

## 4. 文档站与展示工具

推荐使用 VitePress 将仓库 Markdown 构建为工程产品文档站：

- Markdown 仍是唯一内容源；
- 文件目录直接形成页面路由；
- 支持导航、侧边栏、本页目录和本地全文搜索；
- 支持深色与浅色主题；
- 可生成纯静态 HTML；
- 可部署到 Nginx、GitHub Pages、对象存储或内网文件服务器；
- 可以将静态产物随版本归档，形成可离线评审的文档快照。

推荐命令：

```bash
pnpm docs:dev       # 本地热更新
pnpm docs:build     # 生成静态 HTML
pnpm docs:preview   # 预览生产构建
```

文档站构建应加入 CI。构建失败通常意味着链接失效、Markdown 语法不兼容、导航指向不存在页面或配置错误。需要注意：文档站成功构建只说明展示正确，不表示文档内容已经完成业务评审。

## 5. 传统 AI 项目的改造方法

传统 AI 项目常见状态包括：README 承载所有说明、设计文件散落、计划和任务重复、需求无法追踪、模型实验与产品测试混在一起、部署操作依赖个人经验。改造时不建议一次重写全部内容，而应先建立信息架构，再逐步迁移事实源。

### 5.1 第一步：盘点现状

建立文档清单，并给每份文档标注：

- 当前、历史、草稿或未知状态；
- 产品、架构、需求、计划、测试、实验、部署或发布类型；
- 是否仍被代码或 README 引用；
- 是否与其他文件重复；
- 是否包含无法验证的完成状态；
- 应保留、合并、迁移还是归档。

此阶段只整理事实，不应顺手改变业务设计。

### 5.2 第二步：确定权威性和命名

先定义目录职责和冲突优先级，再移动文件。建议明确：

1. `AGENTS.md` 约束工程红线；
2. Accepted ADR 约束长期决策；
3. 全局架构约束模块边界；
4. 功能 SDD 定义当前行为；
5. 工程规则定义实施方式；
6. Deliverables 和 Archive 仅作历史证据。

### 5.3 第三步：整理现有文档

- 合并重复的 `design` 和 `architecture`；
- 将 ADR 收入 `architecture/adr/`，但保留独立文档类型；
- 将散落的 migration、release、guide、test report 分别归位；
- 删除只起兼容导航作用且已无引用的空目录；
- 将被替代的旧需求、旧架构和旧测试规格移入 Archive；
- 更新所有相对链接并执行自动检查。

### 5.4 第四步：引入功能 SDD

不要尝试立即为所有历史功能补齐完整 SDD。优先选择：

- 即将开发的新功能；
- 正在重构的高风险功能；
- 跨多个模块的功能；
- 需要模型、Tool、MCP 或外部系统协作的功能；
- 曾经频繁发生回归的功能。

为这些功能建立最小规格包，再随着复杂度增加 contracts、UI、state machine 和 traceability。

### 5.5 第五步：建立质量和评测体系

- 盘点仓库中真实存在的测试命令，不虚构回归项；
- 建立全项目回归目录和触发条件；
- 将功能测试规格、实际执行证据、阶段评审结论分开；
- 将性能、Agent 能力、检索质量和模型对比放入独立 Benchmark；
- 未实际执行的测试必须标记为未执行，而不是通过。

### 5.6 第六步：接入文档站和 CI

- 建立 VitePress 首页、导航和侧边栏；
- 启用本地全文搜索；
- 使用相对资源路径生成可迁移静态站；
- 在 CI 中执行 Markdown 链接检查和文档构建；
- 将静态产物作为版本附件或内部文档站发布。

## 6. 改造 Roadmap

| 阶段 | 目标 | 主要产物 | 完成标准 |
| --- | --- | --- | --- |
| M0：盘点 | 看清现状与重复关系 | 文档清单、分类、事实源冲突表 | 所有现有文档都有处理结论 |
| M1：信息架构 | 建立统一目录和权威性 | `docs/README.md`、目录职责、冲突优先级 | 不再存在两个当前事实源 |
| M2：归位清理 | 移动散落文件并归档旧文档 | architecture、guides、quality、archive 等目录 | 根目录无散落专题文件，链接检查通过 |
| M3：工程治理 | 约束人和编码智能体的工作方式 | `AGENTS.md`、engineering、SDD 工作流、评审清单 | 新变更能够按规则找到输入和出口 |
| M4：SDD 试点 | 用一个真实功能跑通闭环 | requirements、design、tasks、tests、status、traceability | 需求到测试可追踪，状态真实 |
| M5：质量体系 | 建立回归、阶段测试和发布验收 | quality、regression suite、release report | 发布门禁有可执行证据 |
| M6：Benchmark | 建立平台特征评测 | methodology、catalog、dataset、baseline、report | 结果可复现、可比较、不过度解读 |
| M7：文档产品化 | 提供专业浏览和离线展示 | VitePress、搜索、静态 HTML、CI | 文档构建稳定，导航覆盖全部事实源 |
| M8：持续治理 | 让文档与代码共同演进 | 定期审计、归档、基线和状态更新 | 无长期死链、陈旧状态和重复规格 |

推荐以一个真实跨模块功能作为 M4 试点。试点闭环后再复制模板，而不是先批量生成大量空文档。

## 7. 从文档组织提炼的 AI 编程方法论

可以将整套实践压缩为一个简洁循环：

```text
定界 → 规格化 → 拆解 → 实现 → 验证 → 留证 → 反馈
```

### 7.1 定界

先确认目标、范围、非目标、模块边界、权限和不可破坏的约束。AI 在边界不清晰时不应直接扩大实现范围。

### 7.2 规格化

把自然语言需求转换为稳定 ID、业务规则、契约、状态变化和可测试的验收条件。复杂功能先更新规格，再开始编码。

### 7.3 拆解

任务应足够小、依赖清晰、可独立验证，并明确修改范围、完成条件和关联测试。任务不是需求的重复描述，而是实现规格的动作单元。

### 7.4 实现

编码智能体先读取规则、架构、当前功能规格、任务和测试，再做最小、可回滚的修改。遇到实现与规格冲突时，先处理冲突，不以代码事实静默覆盖设计。

### 7.5 验证

验证应覆盖静态检查、单元测试、契约测试、集成测试、专项回归和必要的人工验收。根据风险选择验证范围，而不是机械地只运行一个命令。

### 7.6 留证

记录实际执行的命令、环境、提交、结果和失败项。区分“未执行”“失败”“通过”和“风险接受”，禁止用模糊措辞代替证据。

### 7.7 反馈

实现和测试暴露的新约束应回写需求、架构、ADR、测试规格或工程规则；被替代的内容进入归档。这样下一轮 AI 编程读取到的是更新后的工程现实。

## 8. 最小实用规则

如果团队暂时无法采用完整体系，至少执行以下十条：

1. 每类事实只维护一个权威位置；
2. 编码前先读 `AGENTS.md`、全局架构和当前功能规格；
3. 跨模块功能必须有独立 SDD；
4. 需求必须有稳定 ID 和验收条件；
5. 任务必须链接需求、设计和测试；
6. 公共契约变化必须先更新契约和兼容策略；
7. 已写文档、已实现、已测试和已发布分别记录；
8. 测试与 Benchmark 分开管理；
9. 当前规格与历史评审快照分开管理；
10. 文档链接检查和静态站构建进入 CI。

## 9. 实践判断标准

一个适合 AI 编程的工程文档体系，不以文件数量衡量，而应能让新开发者或编码智能体快速回答以下问题：

- 这个产品解决什么问题？
- 当前系统的模块和依赖边界是什么？
- 这项功能现在应该如何工作？
- 为什么选择当前方案？
- 下一步具体执行哪个任务？
- 完成条件和测试方法是什么？
- 当前真实状态和阻塞项是什么？
- 哪些内容已经被替代，历史结论在哪里？
- 这个版本实际验证和发布了什么？

如果这些问题可以从固定入口快速、无冲突地得到答案，文档就已经从“说明材料”转变为可驱动 AI 编程的工程基础设施。
